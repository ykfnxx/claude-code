# 第二章：核心引擎分析 - QueryEngine 与 Query Loop

## 概览

Claude Code 的核心推理引擎由两个紧密协作的模块构成：`QueryEngine`（`src/QueryEngine.ts`，约1295行）和 `query loop`（`src/query.ts`，约1729行）。前者是对话级别的状态管理器，负责会话生命周期、消息持久化、结构化输出等横切关注点；后者是推理级别的无限循环，负责上下文管理、模型调用、工具执行和终止判定。

两者的关系是包裹与内核的关系。`QueryEngine` 在外层管理跨 turn 的可变状态（`mutableMessages`、`totalUsage`、`permissionDenials`），每次用户发送消息时调用 `submitMessage()`，进入一轮完整的 query 生命周期。`query()` 函数则作为异步生成器，在无限循环中迭代，每次迭代代表一次模型调用及其后续的工具执行。

```
用户消息
  |
  v
+------------------+
|   QueryEngine    |   <-- 对话级状态管理器
|  submitMessage() |
+--------+---------+
         |
         v
+------------------+
|   processUserInput|  <-- 斜杠命令、附件处理
+--------+---------+
         |
         v
+------------------+
|      query()     |   <-- 异步生成器入口
+--------+---------+
         |
         v
+------------------+
|    queryLoop()   |   <-- while(true) 无限循环
|  +------------+  |
|  | 上下文压缩  |  |   <-- snip / microcompact / collapse / autocompact
|  +------------+  |
|  | 模型调用    |  |   <-- deps.callModel → streaming API
|  +------------+  |
|  | 工具执行    |  |   <-- StreamingToolExecutor / runTools
|  +------------+  |
+--------+---------+
         |
         v
    Terminal / Continue
```

## 一、QueryEngine：对话状态管理器

### 1.1 核心职责

`QueryEngine` 是一个类（`src/QueryEngine.ts:184`），遵循"一个对话一个实例"的原则。它的核心职责包括：

- 管理 `mutableMessages`：对话中所有消息的可变数组，跨 turn 持久化
- 管理 `abortController`：支持用户中断当前推理过程
- 追踪 `permissionDenials`：记录权限拒绝事件，供 SDK 调用者感知
- 累计 `totalUsage`：跟踪所有 API 调用的 token 消耗
- 管理 `readFileState`：文件状态缓存（LRU），用于去重和内存附件
- 管理 `discoveredSkillNames`：turn 级技能发现追踪

### 1.2 配置体系

`QueryEngineConfig`（第130行）定义了引擎的全部可配置项：

```typescript
type QueryEngineConfig = {
  cwd: string                    // 工作目录
  tools: Tools                   // 可用工具集
  commands: Command[]            // 斜杠命令集
  mcpClients: MCPServerConnection[]  // MCP 客户端
  agents: AgentDefinition[]      // 子代理定义
  customSystemPrompt?: string    // 自定义系统提示（替换默认）
  appendSystemPrompt?: string    // 追加系统提示
  maxTurns?: number              // 最大迭代轮次
  maxBudgetUsd?: number          // 预算限制（美元）
  jsonSchema?: Record<string, unknown>  // 结构化输出 schema
  // ... 其他配置
}
```

其中 `customSystemPrompt` 和 `appendSystemPrompt` 的区别值得注意：前者完全替换默认系统提示，后者在其后追加。`jsonSchema` 配合 `SyntheticOutputTool` 实现结构化输出功能。

### 1.3 submitMessage 生命周期

`submitMessage()`（第209行）是 `QueryEngine` 的唯一公共方法，它是一个异步生成器，每次调用代表一个完整的用户 turn。其执行流程如下：

```
submitMessage(prompt)
  |
  +--> 1. setCwd(cwd)                   // 设置工作目录
  +--> 2. fetchSystemPromptParts()       // 获取系统提示词
  +--> 3. 拼装 systemPrompt              // custom + memory + append
  +--> 4. registerStructuredOutputEnforcement()  // 结构化输出注册
  +--> 5. processUserInput()             // 处理用户输入（含斜杠命令）
  +--> 6. recordTranscript()             // 持久化到会话存储
  +--> 7. 加载 skills/plugins            // getSlashCommandToolSkills + loadAllPluginsCacheOnly
  +--> 8. yield buildSystemInitMessage() // 发送系统初始化消息
  +--> 9. query() loop                   // 进入推理循环
  +--> 10. 归一化并 yield 结果消息
  +--> 11. yield result message           // 发送最终结果
```

#### 1.3.1 系统提示词构建

系统提示词的构建发生在第286-325行，采用三层叠加策略：

1. **默认层**：`fetchSystemPromptParts()` 获取默认系统提示，包含工具描述、权限上下文、MCP 客户端信息
2. **内存层**：如果存在自定义系统提示且设置了 `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE`，注入内存机制提示词
3. **追加层**：`appendSystemPrompt` 附加在最后

```typescript
const systemPrompt = asSystemPrompt([
  ...(customPrompt !== undefined ? [customPrompt] : defaultSystemPrompt),
  ...(memoryMechanicsPrompt ? [memoryMechanicsPrompt] : []),
  ...(appendSystemPrompt ? [appendSystemPrompt] : []),
])
```

#### 1.3.2 会话持久化

会话持久化采用分级策略（第450-463行）：

- **bare mode**：fire-and-forget，不阻塞主流程（~4ms on SSD）
- **普通模式**：await 写入完成
- **cowork 模式**：写入后额外调用 `flushSessionStorage()` 确保磁盘落盘

这个设计考虑了真实场景：如果用户在发送消息后立刻点击 Stop，进程可能在 API 响应前终止。提前写入用户消息确保了 `--resume` 功能总能找到会话入口点。

#### 1.3.3 流式消息处理

在 `for await (const message of query(...))` 循环中（第675行），`QueryEngine` 处理多种消息类型：

| 消息类型 | 处理方式 |
|---------|---------|
| `assistant` | 推送至 `mutableMessages`，yield 归一化消息 |
| `user` | 推送至 `mutableMessages`，记录 transcript |
| `progress` | 推送至 `mutableMessages`，fire-and-forget 记录 |
| `stream_event` | 处理 `message_start`/`message_delta`/`message_stop` 用于 usage 追踪 |
| `attachment` | 处理 `structured_output`、`max_turns_reached`、`queued_command` |
| `system` (compact_boundary) | 写入 transcript，flush preservedSegment |
| `tombstone` | 跳过（控制信号） |

### 1.4 结构化输出

当配置了 `jsonSchema` 且工具集包含 `SyntheticOutputTool` 时（第328-333行），引擎通过 `registerStructuredOutputEnforcement()` 注册函数钩子。这确保模型输出遵循用户提供的 JSON Schema，SyntheticOutputTool 充当输出约束的执行者。

## 二、Query Loop：推理级无限循环

### 2.1 架构设计

`queryLoop()`（`src/query.ts:241`）是一个 `while(true)` 无限循环，使用可变 `State` 对象在迭代间传递状态：

```typescript
type State = {
  messages: Message[]                        // 当前消息序列
  toolUseContext: ToolUseContext              // 工具使用上下文
  autoCompactTracking: AutoCompactTrackingState | undefined  // 自动压缩追踪
  maxOutputTokensRecoveryCount: number       // 输出 token 恢复计数
  hasAttemptedReactiveCompact: boolean       // 是否已尝试响应式压缩
  maxOutputTokensOverride: number | undefined // 输出 token 覆盖
  pendingToolUseSummary: Promise<...> | undefined // 挂起的工具摘要
  stopHookActive: boolean | undefined        // 停止钩子状态
  turnCount: number                          // 轮次计数
  transition: Continue | undefined           // 上次迭代继续的原因
}
```

`State` 采用不可变替换模式：每次 `continue` 时创建新的 `State` 对象，而非逐字段修改。这使得代码路径更清晰，也便于追踪转换原因。

### 2.3 上下文压缩管道

上下文管理是 query loop 最复杂的子系统，包含四个逐级执行的压缩策略：

#### 2.3.1 Snip Compact（HISTORY_SNIP）

位于 `src/services/compact/snipCompact.ts`，在迭代的最早期执行。它的策略是"剪刀式"裁剪：保留近期的对话历史，将较早的部分替换为摘要边界标记。`snipTokensFreed` 会被传递给 autocompact 的阈值检查，确保阈值计算反映实际释放的 token 数。

#### 2.3.2 Microcompact

执行位置在第414行，采用两种策略：

- **缓存编辑（cachedMC）**：利用 API 的 `cache_deleted_input_tokens` 字段实现零成本压缩
- **基于时间驱逐**：对长时间未引用的历史工具结果进行淘汰

缓存编辑的边界消息延迟到 API 响应后 yield，使用实际的 `cache_deleted_input_tokens` 而非客户端估算值，这保证了准确性。

#### 2.3.3 Context Collapse（CONTEXT_COLLAPSE）

位于 `src/services/contextCollapse/`，在 autocompact 之前执行。它不是删除消息，而是在读取时投影一个"折叠视图"。折叠后的消息保存在独立的 collapse store 中，不影响 REPL 的完整历史。这种设计使得折叠可以跨 turn 持续：`projectView()` 每次入口时重放 commit log。

折叠的另一个关键用途是错误恢复。当 API 返回 413（prompt too long）时，`recoverFromOverflow()` 会排空已暂存的折叠，提供一种比完整压缩更轻量的恢复路径。

#### 2.3.4 Auto-compact

自动压缩是最后也是最重的策略（第454行）。当 token 计数超过阈值时触发一次完整的对话压缩，将历史消息替换为摘要消息。它包含 circuit breaker 机制：`consecutiveFailures` 追踪连续失败次数，超过阈值后停止重试。

压缩结果通过 `buildPostCompactMessages()` 构建后 yield 给调用者，并替换 `messagesForQuery` 进入下一轮迭代。`taskBudget.remaining` 在压缩时进行累计扣减，确保压缩后的 remaining 值准确反映实际消耗。

### 2.4 模型调用与流式处理

模型调用通过 `deps.callModel()` 完成（第659行），这是一个依赖注入点。生产环境使用 `productionDeps()`，测试时可以替换为 mock。

调用参数的构建涉及多个策略性决策：

- **模型选择**：`getRuntimeMainLoopModel()` 根据权限模式（plan 模式超过 200k token 时降级）动态选择模型
- **Thinking 配置**：`toolUseContext.options.thinkingConfig` 支持自适应模式
- **Task Budget**：压缩后通过 `taskBudgetRemaining` 告知服务端已消耗的预算
- **工具刷新**：`refreshTools` 在 turn 间刷新工具集，捕获新连接的 MCP 服务

流式处理中的一个关键设计是"withhold"机制（第799-825行）：可恢复的错误（prompt too long、max output tokens、media size error）会被暂扣，不立即 yield 给调用者。只有当所有恢复路径都失败时，错误才会浮出水面。这避免了中间态错误泄露给 SDK 消费者（如桌面客户端）导致会话意外终止。

### 2.5 错误恢复策略

query loop 实现了多层次的错误恢复：

```
API 错误
  |
  +-- Prompt Too Long (413)
  |     |-- 尝试 Context Collapse drain (轻量)
  |     |-- 尝试 Reactive Compact (完整压缩)
  |     |-- 两者均失败 → yield 错误，返回
  |
  +-- Max Output Tokens
  |     |-- Escalate: 8k → 64k (单次)
  |     |-- Recovery loop: 注入恢复消息 (最多3次)
  |     |-- 全部失败 → yield 错误
  |
  +-- Media Size Error
  |     |-- Reactive Compact strip-retry
  |     |-- 失败 → yield 错误
  |
  +-- Fallback Triggered
        |-- 切换到 fallbackModel
        |-- 清空 assistantMessages
        |-- Strip thinking signatures
        |-- 重试整个请求
```

`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3` 限制了恢复尝试次数，防止无限循环。恢复消息使用 `isMeta: true` 标记，指示模型直接从断点继续，不要道歉或重述。

### 2.6 Stop Hooks

当模型产生纯文本回复（无 `tool_use`）时，进入停止钩子评估（第1267行）。`handleStopHooks()` 检查注册的停止钩子，可能产生三种结果：

1. **正常终止**：返回 `{ reason: 'completed' }`
2. **钩子阻止继续**：返回 `{ reason: 'stop_hook_prevented' }`
3. **钩子产生阻塞错误**：注入错误消息并继续下一轮迭代（`transition: 'stop_hook_blocking'`）

### 2.7 工具执行后的状态流转

工具执行完成后，query loop 进入状态构建阶段（第1715-1728行）：

```typescript
const next: State = {
  messages: [...messagesForQuery, ...assistantMessages, ...toolResults],
  toolUseContext: toolUseContextWithQueryTracking,
  autoCompactTracking: tracking,
  turnCount: nextTurnCount,
  maxOutputTokensRecoveryCount: 0,
  hasAttemptedReactiveCompact: false,
  pendingToolUseSummary: nextPendingToolUseSummary,
  maxOutputTokensOverride: undefined,
  stopHookActive,
  transition: { reason: 'next_turn' },
}
state = next
```

`messages` 数组被重建为当前查询消息 + 助手消息 + 工具结果的拼接。`maxOutputTokensRecoveryCount` 和 `hasAttemptedReactiveCompact` 在每次新 turn 时重置，允许独立的恢复尝试。

### 2.8 终止条件

query loop 有多个终止出口：

| 终止原因 | 触发条件 |
|---------|---------|
| `completed` | 模型返回纯文本，无 tool_use |
| `aborted_streaming` | 用户在流式响应期间中断 |
| `aborted_tools` | 用户在工具执行期间中断 |
| `blocking_limit` | token 计数超过硬阻断阈值 |
| `max_turns` | 超过配置的最大轮次 |
| `prompt_too_long` | 所有压缩恢复路径失败 |
| `image_error` | 图片尺寸错误且无法恢复 |
| `model_error` | API 调用抛出不可恢复错误 |
| `stop_hook_prevented` | 停止钩子阻止继续 |
| `hook_stopped` | 工具执行后钩子阻止继续 |
| `token_budget_continuation` | Token 预算超支继续（特殊情况） |

## 三、Thinking 规则

query.ts 的第155-163行记录了一套严格的 thinking block 规则，被注释称为"巫师的冥想规则"：

1. 包含 thinking 或 redacted_thinking block 的消息，必须属于 `max_thinking_length > 0` 的查询
2. thinking block 不能是 block 序列中的最后一个
3. thinking block 在整个助手轨迹（trajectory）中必须被保留，包括后续的 `tool_result` 和下一个助手消息

违反这些规则会导致 API 错误，需要"一整天的调试和抓头发"来排查。

## 四、流式工具执行器

`StreamingToolExecutor`（`src/services/tools/StreamingToolExecutor.ts`，约530行）在流式响应到达时立即开始执行工具，而不必等待整个响应完成。

### 4.1 并发控制

每个工具实现 `isConcurrencySafe(input)` 方法，声明是否可以与其他工具并行执行：

- **并发安全**（如 Read、Glob）：可以与其他并发安全工具同时运行
- **非并发安全**（如 Edit、Write）：必须独占执行，等待所有前序工具完成

### 4.2 Sibling Abort

当一个非并发安全工具（特别是 BashTool）出错时，`siblingAbortController` 会立即终止所有正在运行的兄弟子进程。这是 `toolUseContext.abortController` 的子控制器，终止它不会导致整个 turn 结束。

### 4.3 Streaming Fallback

当 API 触发 streaming fallback（模型过载降级）时：

1. 已产生的 assistant messages 变为 tombstone 消息，从 UI 和 transcript 中移除
2. `streamingToolExecutor.discard()` 取消所有挂起和进行中的工具
3. 创建新的 `StreamingToolExecutor` 实例
4. 切换到 fallback 模型重试整个请求

## 五、依赖注入与可测试性

query loop 的依赖通过 `QueryDeps` 接口注入（`src/query/deps.ts`）：

- `callModel`：模型调用函数
- `microcompact`：微压缩函数

生产环境使用 `productionDeps()`，测试可以注入 mock 实现。这种设计使得 query loop 的核心逻辑可以脱离 API 和文件系统进行单元测试。

## 六、关键设计洞察

### 6.1 不可变状态替换

每次迭代通过 `state = { ... }` 创建新的 State 对象，而非修改已有字段。这使得追踪转换原因变得简单（`transition` 字段），也避免了跨迭代的意外状态泄漏。

### 6.2 延迟边界消息

Microcompact 的缓存编辑边界消息延迟到 API 响应后 yield，使用真实的 `cache_deleted_input_tokens` 而非估算值。这种延迟-验证模式在多个地方出现，体现了"宁可多等一拍也要确保准确"的设计哲学。

### 6.3 Fire-and-forget Transcript

对于 assistant 消息的 transcript 写入采用 fire-and-forget（第728行），不阻塞主流程。这是因为 claude.ts 的流式机制会在每个 content block 后 yield，await 会阻塞下一个 block 的消费。

### 6.4 分级错误处理

错误恢复采用分层策略：轻量恢复（collapse drain）优先，重量恢复（reactive compact）在后，最终才是错误浮出。这最大程度减少了因临时性 token 超限导致的用户可见错误。
