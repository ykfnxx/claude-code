# 第七章：工具系统

## 概览

Claude Code 的工具系统是一个分层、可扩展的执行框架，涵盖类型定义、注册发现、验证授权、并发执行和结果管理全生命周期。系统的核心文件包括：

| 文件 | 路径 | 行数 | 职责 |
|-----|------|------|------|
| Tool 类型 | `src/Tool.ts` | ~792 | 工具接口、类型定义、buildTool 工厂 |
| 工具注册 | `src/tools.ts` | ~389 | 全量列表、按模式过滤、MCP 合并 |
| 工具执行 | `src/services/tools/toolExecution.ts` | ~1745 | 验证管道、权限检查、钩子执行 |
| 流式执行器 | `src/services/tools/StreamingToolExecutor.ts` | ~530 | 并发控制、sibling abort、fallback |
| 工具钩子 | `src/services/tools/toolHooks.ts` | - | Pre/Post tool use hooks |
| 权限系统 | `src/hooks/toolPermission/` | - | 权限模式、分类器、规则匹配 |
| 结果预算 | `src/utils/toolResultStorage.ts` | - | 结果大小管理、磁盘持久化 |

## 一、Tool 类型系统

### 1.1 Tool 接口

`Tool` 类型（`src/Tool.ts:362`）是所有工具的核心接口，定义了一个完整的工具需要实现的全部方法：

### 1.2 输入 Schema

每个工具必须定义 `inputSchema`，使用 Zod v4（`import type { z } from 'zod/v4'`）。Schema 同时用于：

- API 层面的工具定义（告诉模型参数结构）
- 运行时输入验证（`inputSchema.safeParse`）
- MCP 工具的 JSON Schema 转换（`inputJSONSchema` 可选，跳过 Zod→JSON 转换）

### 1.3 buildTool 工厂函数

`buildTool()`（第783行）是一个泛型工厂函数，为部分定义的工具填充安全默认值：

```typescript
const TOOL_DEFAULTS = {
  isEnabled: () => true,                    // 默认启用
  isConcurrencySafe: (_input?) => false,    // 默认不并发安全
  isReadOnly: (_input?) => false,           // 默认写操作
  isDestructive: (_input?) => false,        // 默认非破坏性
  checkPermissions: (input, _ctx?) =>       // 默认允许
    Promise.resolve({ behavior: 'allow', updatedInput: input }),
  toAutoClassifierInput: (_input?) => '',   // 默认跳过分类器
  userFacingName: (_input?) => '',          // 默认使用 tool.name
}
```

这些默认值遵循"fail-closed"原则：`isConcurrencySafe` 默认 false，`isReadOnly` 默认 false，确保新工具在明确声明之前不会获得危险的并发或只读特权。

### 1.4 ToolUseContext

`ToolUseContext`（第158行）是工具执行时的运行时上下文，包含工具执行所需的全部信息：


### 1.5 ToolPermissionContext

`ToolPermissionContext`（第123行）定义了权限检查的上下文：

```typescript
type ToolPermissionContext = DeepImmutable<{
  mode: PermissionMode                        // 权限模式
  additionalWorkingDirectories: Map<...>      // 额外工作目录
  alwaysAllowRules: ToolPermissionRulesBySource // 始终允许规则
```

`DeepImmutable` 确保权限上下文在工具执行期间不被修改，所有字段都是只读的。

## 二、工具注册与发现

### 2.1 getAllBaseTools

`getAllBaseTools()`（`src/tools.ts:193`）返回当前环境下所有可用的内置工具列表。工具注册采用条件导入策略，通过 `bun:bundle` 的 `feature()` 函数实现编译时死代码消除：

```typescript
// 始终加载的核心工具（约15个）
AgentTool, TaskOutputTool, BashTool, FileReadTool,
FileEditTool, FileWriteTool, NotebookEditTool,
WebFetchTool, TodoWriteTool, WebSearchTool, TaskStopTool,
AskUserQuestionTool, SkillTool, EnterPlanModeTool, BriefTool

// 条件加载的特性工具
...(feature('PROACTIVE') ? [SleepTool] : []),
...(feature('AGENT_TRIGGERS') ? [CronCreateTool, ...] : []),
...(feature('MONITOR_TOOL') ? [MonitorTool] : []),
...(feature('WEB_BROWSER_TOOL') ? [WebBrowserTool] : []),
...(feature('WORKFLOW_SCRIPTS') ? [WorkflowTool] : [])
```

条件导入确保未启用的特性不会增加包体积，也不会在模块评估时产生副作用。

### 2.2 getTools

`getTools(permissionContext)`（第271行）根据权限上下文过滤工具：

```
getAllBaseTools()
  |
  +-- 移除 specialTools (ListMcpResources, ReadMcpResource, SyntheticOutput)
  |
  +-- filterToolsByDenyRules()
  |     按名称匹配 alwaysDenyRules，整体拒绝的工具直接排除
  |
  +-- REPL 模式处理
  |     如果 REPLTool 可用，隐藏 REPL_ONLY_TOOLS 中的原始工具
  |
  +-- isEnabled() 过滤
        最终检查每个工具的 isEnabled() 方法
```

### 2.3 assembleToolPool

`assembleToolPool(permissionContext, mcpTools)`（第345行）是工具池合并的单一真相源：

```
builtInTools (getTools)
  |
  +-- 按 name 排序
  |
mcpTools (from appState.mcp.tools)
  |
  +-- filterToolsByDenyRules
  +-- 按 name 排序
  |
  +-- concat + uniqBy('name')
       内置工具优先，MCP 工具按需补充
```

排序策略值得注意：内置工具保持为一个连续的前缀（prefix），服务端的 `claude_code_system_cache_policy` 在最后一个内置工具后放置全局缓存断点。如果 MCP 工具混入内置工具之间，每次 MCP 配置变化都会使所有下游缓存失效。

## 三、工具验证管道

工具验证管道是 Claude Code 安全模型的核心防线，定义在 `src/services/tools/toolExecution.ts`。每个工具调用都要经过以下完整的管道：

```
模型输出 tool_use block
  |
  v
+-----------------------------------------------------------------+
|              工具验证管道 (toolExecution.ts)                      |
+-----------------------------------------------------------------+
|                                                                   |
|  Step 1: Tool Lookup (findToolByName)                            |
|  |  在当前工具集中查找，未找到则尝试 deprecated alias fallback     |
|  |  仍未找到 → yield "No such tool available" 错误               |
|  v                                                               |
|  Step 2: Abort Check                                             |
|  |  检查 abortController.signal.aborted                          |
|  |  已中断 → yield 取消消息，return                              |
|  v                                                               |
|  Step 3: Zod Schema Validation (inputSchema.safeParse)           |
|  |  类型级别的严格验证                                           |
|  |  失败 → yield InputValidationError，附加 schema hint          |
|  v                                                               |
|  Step 4: Custom Validation (tool.validateInput)                  |
|  |  工具特定的业务逻辑验证                                       |
|  |  失败 → yield 工具自定义错误消息                              |
|  v                                                               |
|  Step 5: Pre-Tool Hooks (runPreToolUseHooks)                     |
|  |  执行用户定义的 pre-tool-use 钩子                             |
|  |  钩子可能: allow / deny / modify input                       |
|  v                                                               |
|  Step 6: Permission Check (canUseTool)                           |
|  |  检查 always-allow rules → deny rules → ask rules             |
|  |  Auto mode: yoloClassifier 自动分类                           |
|  |  Default mode: 弹出权限对话框                                 |
|  |  Denied → yield 拒绝消息 + runPostToolUseFailureHooks         |
|  v                                                               |
|  Step 7: Tool Execution (tool.call)                              |
|  |  实际执行工具逻辑                                             |
|  |  支持 onProgress 回调报告进度                                 |
|  |  异常 → yield 运行时错误消息                                  |
|  v                                                               |
|  Step 8: Post-Tool Hooks (runPostToolUseHooks)                   |
|  |  成功: runPostToolUseHooks                                    |
|  |  失败: runPostToolUseFailureHooks                             |
|  v                                                               |
|  Step 9: Result Budget Enforcement (applyToolResultBudget)       |
|  |  超大结果持久化到磁盘                                         |
|  |  替换为预览 + 文件路径                                       |
|  v                                                               |
|  Step 10: Result Return                                          |
|     yield { message: toolResultMessage, contextModifier? }      |
|                                                                   |
+-----------------------------------------------------------------+
```

### 3.1 Step 1: Tool Lookup

工具查找分两阶段进行（`toolExecution.ts:345-356`）：

```typescript
// 先在当前可用工具集（模型看到的）中查找
let tool = findToolByName(toolUseContext.options.tools, toolName)

// 未找到时，在全量基础工具集中查找 alias
if (!tool) {
  const fallbackTool = findToolByName(getAllBaseTools(), toolName)
  if (fallbackTool && fallbackTool.aliases?.includes(toolName)) {
    tool = fallbackTool
  }
}
```

alias fallback 机制支持工具重命名后的向后兼容。例如，旧的 `KillShell` 现在是 `TaskStop` 的 alias，旧 transcript 中对 `KillShell` 的调用仍能正常解析。

### 3.2 Step 3: Zod Schema Validation

Zod 验证（第615行）使用 `inputSchema.safeParse(input)`，这比 `parse` 更安全，不会抛出异常：

```typescript
const parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) {
  let errorContent = formatZodValidationError(tool.name, parsedInput.error)
  // 如果工具是 deferred 的（schema 未发送），附加提示
  const schemaHint = buildSchemaNotSentHint(tool, messages, tools)
  if (schemaHint) {
    errorContent += schemaHint
  }
  return [{ message: createUserMessage({ ... }) }]
}
```

`buildSchemaNotSentHint()` 是一个精巧的设计：当工具是延迟加载的（`defer_loading: true`），模型没有收到完整的 schema，参数类型推断会出错（比如把数组输出为字符串）。提示信息引导模型先调用 `ToolSearchTool` 加载工具 schema，再重试调用。

### 3.3 Step 4: Custom Validation

`tool.validateInput()` 是工具特定的业务逻辑验证层（第683行），在 Zod 类型验证通过后执行。例如，`FileEditTool` 可能验证目标文件是否存在，`BashTool` 可能验证命令格式。

### 3.4 Step 5-6: Hooks 与 Permission

Pre-tool hooks 和权限检查是安全模型的两道关卡，执行顺序是先 hooks 后权限：

- **Pre-tool hooks**：用户定义的 Shell 命令钩子，可以在工具执行前修改输入、拒绝执行或允许执行
- **Permission check**：基于规则和用户决策的授权检查

BashTool 有一个特殊优化：在 pre-tool hooks 执行的同时，`startSpeculativeClassifierCheck()` 并行启动分类器检查，减少用户感知的延迟（第740-749行）。

### 3.5 Step 7: Tool Execution

`tool.call()` 是实际的工具执行（`src/Tool.ts:379`），签名为：

```typescript
call(
  args: z.infer<Input>,
  context: ToolUseContext,
  canUseTool: CanUseToolFn,
  parentMessage: AssistantMessage,
  onProgress?: ToolCallProgress<P>,
): Promise<ToolResult<Output>>
```

`onProgress` 回调允许工具在长时间执行中报告进度（如 Bash 命令的部分输出、文件读取的字节数）。进度消息通过 `createProgressMessage()` 包装后 yield 给调用者。

### 3.6 Step 9: Result Budget Enforcement

`applyToolResultBudget()`（`src/utils/toolResultStorage.ts`）对超大工具结果进行管理：

- 每条消息有一个聚合工具结果预算
- 超过 `maxResultSizeChars` 的结果持久化到磁盘
- 工具收到的是预览文本 + 文件路径，而非完整内容

`maxResultSizeChars` 在每个工具上定义。特殊值 `Infinity` 用于 Read 等工具（持久化 Read 的结果会创建 Read→file→Read 的循环）。

## 四、StreamingToolExecutor

### 4.1 设计目标

`StreamingToolExecutor`（`src/services/tools/StreamingToolExecutor.ts`）解决了一个关键问题：在流式响应中，工具调用块逐个到达，不必等待整个响应完成就可以开始执行。

### 4.2 执行模型

```
流式到达 tool_use blocks
  |
  +--> addTool(block, assistantMessage)
  |     |
  |     +--> 查找工具定义
  |     +--> 检查 isConcurrencySafe()
  |     +--> 加入 TrackedTool 队列
  |     +--> 如果条件允许，立即开始执行
  |
  +--> getCompletedResults()
  |     返回已完成但未 yield 的结果
  |
  +--> getRemainingResults()
        返回所有剩余结果（包括仍在执行的）
```

### 4.3 并发控制矩阵

```
              |  正在执行   |   等待中
  -----------+-------------+----------
  并发安全    |  可并行执行  |  立即启动
  非安全      |  排队等待    |  排队等待
  未知工具    |  立即返回错误  |  -
```

并发安全工具（如 Glob、Grep、Read）可以彼此并行执行，但非安全工具（如 Edit、Write、Bash）必须独占运行。

### 4.4 Sibling Abort

当一个工具出错时（特别是 BashTool），所有正在运行的兄弟工具收到合成错误结果：

```
Tool A (executing) --- ERROR
Tool B (executing) --- sibling abort → 合成错误结果
Tool C (queued)    --- 不再启动
Tool D (queued)    --- 不再启动
```

`siblingAbortController` 是 `toolUseContext.abortController` 的子控制器。终止子控制器会杀死兄弟进程，但不会导致整个 turn 中止。

### 4.5 discard 与 Fallback

`discard()` 方法（第69行）在 streaming fallback 场景下使用：

- 标记 `discarded = true`
- 排队的工具不再启动
- 正在执行的工具收到合成错误
- 调用方创建新的 `StreamingToolExecutor` 实例用于重试

## 五、权限系统

### 5.1 PermissionMode

权限模式定义了工具调用的授权策略：

| 模式 | 行为 |
|------|------|
| `default` | 每次新操作弹出权限对话框 |
| `plan` | 计划模式，限制为只读操作 |
| `bypassPermissions` | 跳过所有权限检查（危险） |
| `auto` | yoloClassifier 自动分类，安全操作自动放行 |

### 5.2 canUseTool 授权流程

```
canUseTool(tool, input, context, ...)
  |
  +--> 1. tool.checkPermissions()
  |     工具特定的权限逻辑
  |
  +--> 2. always-allow rules 匹配
  |     用户配置的永久/临时允许规则
  |
  +--> 3. deny rules 匹配
  |     用户配置的拒绝规则（优先级最高）
  |
  +--> 4. Pre-tool hooks 决策
  |     hook 可能返回 allow/deny/ask
  |
  +--> 5. Auto mode classifier (如果 auto 模式)
  |     yoloClassifier 分析工具输入的安全性
  |
  +--> 6. 用户交互 (如果 default 模式)
        弹出权限对话框，用户选择 allow/deny
        可选 "always allow" 记住决策
```

### 5.3 规则匹配

工具权限规则支持通配符模式：

- `Bash(git *)`: 匹配以 `git` 开头的 Bash 命令
- `Edit`: 匹配所有 Edit 操作
- `mcp__server`: 匹配该 MCP 服务器的所有工具

`preparePermissionMatcher()` 方法（`src/Tool.ts:514`）允许工具为 hook 的 `if` 条件准备匹配器，将一次解析的开销分摊到多次匹配中。

## 六、工具结果管理

### 6.1 ToolResult 类型

```typescript
type ToolResult<T> = {
  data: T                                     // 工具输出
  newMessages?: (UserMessage | AssistantMessage | ...)[]  // 附带消息
  contextModifier?: (context: ToolUseContext) => ToolUseContext  // 上下文修改
  mcpMeta?: {                                 // MCP 协议元数据
    _meta?: Record<string, unknown>
    structuredContent?: Record<string, unknown>
  }
}
```

`contextModifier` 只在非并发安全的工具中生效，允许工具修改后续工具的执行上下文。

### 6.2 结果预算

工具结果预算系统管理大型输出的生命周期：

```
tool.call() 返回结果
  |
  +--> processToolResultBlock()
  |     检查结果大小是否超过 maxResultSizeChars
  |
  +--> 超预算?
  |     |-- 是: 持久化到磁盘文件
  |     |       替换为预览 + "Result saved to {path}"
  |     |-- 否: 保持内联
  |
  +--> recordContentReplacement()
        记录替换操作，用于 resume 场景
```

## 七、MCP 工具集成

### 7.1 工具命名

MCP 工具采用 `mcp__{server}__{tool}` 的命名约定：

```typescript
mcpInfo?: {
  serverName: string  // MCP 服务名称（未标准化）
  toolName: string    // 工具名称（未标准化）
}
```

`normalizeNameForMCP()` 处理大小写和特殊字符的标准化，确保工具名在不同环境下一致。

### 7.2 动态发现

MCP 工具在连接建立后动态添加到工具池：

```
MCP 服务器连接
  |
  +--> listTools()
  |     获取服务器提供的工具列表
  |
  +--> 包装为 Tool 对象
  |     inputSchema: 从 MCP schema 转换
  |     call: 通过 MCP 协议调用
  |     isMcp: true
  |
  +--> 存入 appState.mcp.tools
  |
  +--> assembleToolPool() 合并
        下一个 turn 即可使用
```

`refreshTools` 回调（在 `ToolUseContext.options` 中）允许在 turn 间刷新工具集，捕获新连接的 MCP 服务器。

### 7.3 MCP 错误处理

MCP 工具调用可能产生特殊错误：

- **McpAuthError**: 认证失败，触发 re-auth 流程
- **McpToolCallError**: 工具调用失败，包含服务端错误信息
- **Elicitation (-32042)**: 服务端要求用户交互，通过 `handleElicitation` 回调处理

## 八、延迟加载与 ToolSearch

### 8.1 工具延迟机制

当工具集超过一定阈值时，`ToolSearchTool` 启用延迟加载策略：

- `shouldDefer: true` 的工具以 `defer_loading: true` 发送给 API
- 模型只看到工具名和描述，不看到完整 schema
- 需要调用时，模型先调用 `ToolSearchTool` 加载 schema
- `alwaysLoad: true` 的工具不受影响，始终发送完整 schema

### 8.2 发现追踪

`extractDiscoveredToolNames()` 从消息历史中提取已发现的工具名。`buildSchemaNotSentHint()` 利用这个集合检测"schema 未发送"的情况，引导模型正确加载工具。

## 九、设计洞察

### 9.1 安全优先的默认值

`buildTool` 的默认值设计遵循安全优先原则：`isConcurrencySafe` 默认 false，`isReadOnly` 默认 false。新工具必须显式声明自己的安全特性，而不是默认获得特权。

### 9.2 分层验证

验证管道的每一层都有明确的职责边界：Zod 负责类型正确性，`validateInput` 负责业务逻辑，`checkPermissions` 负责授权，hooks 负责用户自定义逻辑。这种分层使得每一层都可以独立测试和修改。

### 9.3 结果预算与内存管理

超大结果持久化到磁盘而非保留在内存中，这对长时间运行的会话尤为重要。Read 工具设置 `maxResultSizeChars: Infinity` 避免了循环依赖（Read→persist→Read），同时通过自身的读取限制控制输出大小。

### 9.4 并发安全声明

`isConcurrencySafe(input)` 是基于输入的判断，而非工具的全局属性。这意味着同一个工具在不同参数下可以有不同的并发行为。例如，BashTool 可能对只读命令（`ls`）声明并发安全，对写命令（`rm`）声明不安全。

### 9.5 缓存友好的工具排序

`assembleToolPool` 将内置工具排序为连续前缀，MCP 工具排序后追加。这确保了内置工具部分在 prompt cache 中保持稳定，MCP 配置变化不会使核心缓存失效。`uniqBy('name', ...)` 保证内置工具在命名冲突时优先，MCP 工具作为补充。
