# 第八章：状态管理

## 概览

Claude Code 的状态管理采用双层架构，将"不需要响应式更新的全局运行时数据"与"需要驱动 UI 渲染的响应式状态"严格分离。这种设计既避免了单一大状态树带来的性能问题，又保证了 Terminal UI 的高效重渲染。

| 层次 | 核心文件 | 行数 | 职责 |
|------|---------|------|------|
| Layer 1: 全局可变状态 | `src/bootstrap/state.ts` | ~1760 | 模块级 singleton，getter/setter 访问 |
| Layer 2: 响应式 Store | `src/state/store.ts` | 34 | Zustand-like 不可变 Store |
| Layer 2: 状态定义 | `src/state/AppStateStore.ts` | 569 | AppState 类型 + 默认值工厂 |
| Layer 2: React 绑定 | `src/state/AppState.tsx` | ~200 | Provider、Hooks、useSyncExternalStore |
| 选择器 | `src/state/selectors.ts` | 76 | 派生状态计算 |
| 副作用处理器 | `src/state/onChangeAppState.ts` | 171 | 状态变更副作用 |
| 视图辅助 | `src/state/teammateViewHelpers.ts` | - | Teammate 视图路由 |

## 一、Layer 1：全局可变状态

### 1.1 设计哲学

`src/bootstrap/state.ts` 是整个应用的"脊髓"--它在依赖图的叶子节点位置，几乎不存在对其他业务模块的导入（仅导入类型和基础工具函数）。文件顶部有明确注释（`state.ts:31`）：

```typescript
// DO NOT ADD MORE STATE HERE - BE JUDICIOUS WITH GLOBAL STATE
```

这个约 1760 行的文件维护一个模块级 `STATE` 单例（`state.ts:429`），通过闭包实现访问隔离。所有外部访问必须通过导出的 getter/setter 函数。

### 1.3 Getter/Setter 模式

访问模式采用闭包隔离的 getter/setter 函数对：

```typescript
// state.ts:429 - 模块级单例
const STATE: State = getInitialState()

// state.ts:431-433 - 典型 getter
export function getSessionId(): SessionId {
  return STATE.sessionId
}

// state.ts:531-533 - 典型 setter (NFC normalization)
export function setCwdState(cwd: string): void {
  STATE.cwd = cwd.normalize('NFC')
}
```

**关键设计点：**

- **路径字符串统一做 NFC normalize**（`state.ts:516-517`），解决 macOS HFS+ 的 NFD 编码问题
- **原子性会话切换**: `switchSession()` 函数（`state.ts:468-479`）同时更新 `sessionId` 和 `sessionProjectDir`，通过信号 `sessionSwitched.emit(sessionId)` 通知订阅者（如并发会话管理器），防止两者漂移
- **会话 ID 继承**: `regenerateSessionId({ setCurrentAsParent: true })`（`state.ts:435-450`）在切换到新会话时保留父会话 ID，用于 plan->implement 等会话谱系追踪
- **交互时间惰性批处理**: `updateLastInteractionTime()`（`state.ts:667-673`）通过 `interactionTimeDirty` 标记将 `Date.now()` 调用延迟到 Ink 渲染帧，避免每次按键都触发
- **滚动排他机制**: `scrollDraining` 标记和 150ms 去抖（`state.ts:792-824`），让后台 interval 在滚动时让出事件循环

### 1.4 成本追踪体系

成本追踪形成一套完整的计量体系，涵盖会话级和 turn 级两个维度：

```

    |
    +-- STATE.modelUsage[model] = modelUsage    // 按模型记录详细用量
    +-- STATE.totalCostUSD += cost              // 累加总费用
    |
    v

getTotalInputTokens()       // sumBy(modelUsage, 'inputTokens')
getTotalOutputTokens()      // sumBy(modelUsage, 'outputTokens')
getTotalCacheReadInputTokens()
getTotalCacheCreationInputTokens()
getTotalWebSearchRequests()
```

Turn 级别的 output token 追踪通过 `snapshotOutputTokensForTurn(budget)` 实现（`state.ts:733-736`），在每次 turn 开始时快照当前 output tokens，支持 token budget 限制和 continuation 计数：

```typescript
let outputTokensAtTurnStart = 0
let currentTurnTokenBudget: number | null = null

export function snapshotOutputTokensForTurn(budget: number | null): void {
  outputTokensAtTurnStart = getTotalOutputTokens()
  currentTurnTokenBudget = budget
  budgetContinuationCount = 0
}

export function getTurnOutputTokens(): number {
  return getTotalOutputTokens() - outputTokensAtTurnStart
}
```

会话恢复时通过 `setCostStateForRestore()`（`state.ts:881-916`）完整还原成本状态，包括调整 `startTime` 使挂钟时间连续累积。

## 二、Layer 2：响应式 Store

### 2.1 Store 原语 (src/state/store.ts)

这是一个仅 34 行的 Zustand-like 不可变 Store 实现：

```typescript
export function createStore<T>(
  initialState: T,
  onChange?: OnChange<T>,
): Store<T> {
  let state = initialState
  const listeners = new Set<Listener>()

  return {
    getState: () => state,

    setState: (updater: (prev: T) => T) => {
      const prev = state
      const next = updater(prev)
      if (Object.is(next, prev)) return   // 引用相等则跳过
      state = next
      onChange?.({ newState: next, oldState: prev })  // 副作用钩子
      for (const listener of listeners) listener()     // 通知订阅者
    },

    subscribe: (listener: Listener) => {
      listeners.add(listener)
      return () => listeners.delete(listener)  // 返回取消订阅函数
    },
  }
}
```

**核心特性：**

- **不可变更新**: `setState` 接受 updater 函数，返回新引用才会触发更新
- **Object.is 优化**: 引用相等时跳过通知，避免无效渲染
- **onChange 钩子**: 状态变更后、通知监听者之前执行副作用

## 三、React 绑定层 (src/state/AppState.tsx)

### 3.1 AppStateProvider

`AppStateProvider`（`AppState.tsx:37-110`）是 Store 的 React 封装：

```
AppStateProvider
    |
    +-- useState(() => createStore(initialState, onChangeAppState))
    |       创建 Store 实例 (仅初始化一次)
    |
    +-- useEffect: 检查 bypass permissions 禁用状态
    |
    +-- useSettingsChange: 监听设置文件变更
    |       applySettingsChange(source, store.setState)
    |
    +-- AppStoreContext.Provider
        +-- HasAppStateContext.Provider (嵌套保护)
            +-- MailboxProvider
                +-- VoiceProvider (feature-gated)
                    +-- {children}
```

**关键设计点：**

- **嵌套保护**: `HasAppStateContext`（`AppState.tsx:36`）防止 `AppStateProvider` 嵌套，嵌套时直接抛出错误
- **React Compiler 优化**: 使用 `_c(13)` 编译器 runtime（`AppState.tsx:38`）进行 memoization，避免不必要的重渲染
- **设置变更同步**: `useSettingsChange` hook 监听磁盘配置文件变化，通过 `applySettingsChange` 同步到 Store
- **VoiceProvider 特性门控**: 使用 `feature('VOICE_MODE')` 进行构建时死代码消除（`AppState.tsx:14-18`），外部构建得到透传版本

### 3.2 useAppState Hook

```typescript
export function useAppState(selector: (state: AppState) => T): T {
  const store = useAppStore()
  const get = () => selector(store.getState())
  return useSyncExternalStore(store.subscribe, get, get)
}
```

基于 React 18 的 `useSyncExternalStore`，实现外部 Store 与 React 渲染的同步。selector 返回的值通过 `Object.is` 比较决定是否重渲染。

**使用规范（源码注释 AppState.tsx:126-141）：**

```typescript
// 正确：选择单个字段
const verbose = useAppState(s => s.verbose)
const model = useAppState(s => s.mainLoopModel)

// 正确：选择已有子对象引用
const { text, promptId } = useAppState(s => s.promptSuggestion)

// 错误：返回新对象 (Object.is 总是 false)
const { a, b } = useAppState(s => ({ a: s.a, b: s.b }))
```

### 3.3 其他 Hooks

| Hook | 说明 |
|------|------|
| `useSetAppState()` | 获取 setState 函数，不订阅任何状态 (稳定引用，永不重渲染) |
| `useAppStateStore()` | 获取完整 Store 对象 (用于传递给非 React 代码) |
| `useAppStateMaybeOutsideOfProvider(selector)` | 安全版本，Provider 外部返回 undefined |

## 四、选择器系统 (src/state/selectors.ts)

选择器模块提供纯函数式的派生状态计算，遵循"简单数据提取，无副作用"原则（`selectors.ts:1-4`）。

### 4.1 getViewedTeammateTask

```typescript
function getViewedTeammateTask(
  appState: Pick<AppState, 'viewingAgentTaskId' | 'tasks'>
): InProcessTeammateTaskState | undefined
```

三重检查链：`viewingAgentTaskId` 存在 -> `tasks[id]` 存在 -> 是 `InProcessTeammateTask` 类型。使用 `Pick` 类型而非完整 `AppState` 减少依赖。

### 4.2 getActiveAgentForInput

```typescript
type ActiveAgentForInput =
  | { type: 'leader' }
  | { type: 'viewed'; task: InProcessTeammateTaskState }
  | { type: 'named_agent'; task: LocalAgentTaskState }
```

决定用户输入路由目标的三级判断：

```
getActiveAgentForInput(state)
    |
    +-- viewingAgentTaskId 指向 InProcessTeammateTask?
    |     -> { type: 'viewed', task }  (输入发往该 teammate)
    |
    +-- viewingAgentTaskId 指向 LocalAgentTask?
    |     -> { type: 'named_agent', task }  (输入发往命名 agent)
    |
    +-- 其他
          -> { type: 'leader' }  (输入发往主 agent)
```

## 五、状态变更副作用 (src/state/onChangeAppState.ts)

`onChangeAppState` 是 Store 的 `onChange` 回调，在每次状态变更后、通知监听者之前执行。它处理跨系统的副作用同步：

### 5.1 权限模式同步

```typescript
// onChangeAppState.ts:65-92
if (prevMode !== newMode) {
  const prevExternal = toExternalPermissionMode(prevMode)
  const newExternal = toExternalPermissionMode(newMode)
  if (prevExternal !== newExternal) {
    notifySessionMetadataChanged({
      permission_mode: newExternal,
      is_ultraplan_mode: isUltraplan,
    })
  }
  notifyPermissionModeChanged(newMode)
}
```

这是权限模式变更的"单一阻塞点"。注释（`onChangeAppState.ts:51-59`）详细解释了为什么需要集中处理：此前有 8+ 条修改路径（Shift+Tab 循环、ExitPlanMode 对话框选项、`/plan` 命令、rewind、bridge 的 `onSetPermissionMode` 等）各自修改 AppState 但不通知外部系统，导致 CCR `external_metadata.permission_mode` 与 CLI 实际模式脱节。

集中处理的设计使得**所有** `setAppState` 调用只要改变了权限模式，就自动同步到 CCR（通过 `notifySessionMetadataChanged`）和 SDK 状态流（通过 `notifyPermissionModeChanged`），各调用点无需修改。

### 5.2 模型设置持久化

```typescript
// 模型被移除 -> 清除设置
if (newState.mainLoopModel === null)
  updateSettingsForSource('userSettings', { model: undefined })

// 模型被设置 -> 写入设置
if (newState.mainLoopModel !== null)
  updateSettingsForSource('userSettings', { model: newState.mainLoopModel })
```

同时通过 `setMainLoopModelOverride()` 同步更新 Layer 1 全局状态中的模型覆盖。

### 5.3 UI 偏好持久化

| 变更 | 持久化到 |
|------|---------|
| `expandedView` | `globalConfig.showExpandedTodos` + `showSpinnerTree` |
| `verbose` | `globalConfig.verbose` |
| `tungstenPanelVisible` | `globalConfig.tungstenPanelVisible` (ant-only) |

`expandedView` 的持久化采用了向后兼容策略：将单个枚举值拆分为两个独立的 boolean 字段（`onChangeAppState.ts:115-128`）。

### 5.4 设置变更缓存清理

当 `settings` 对象引用变更时（`onChangeAppState.ts:156-170`），自动清除三类认证缓存并重新应用环境变量：

```typescript
clearApiKeyHelperCache()
clearAwsCredentialsCache()
clearGcpCredentialsCache()

// 环境变量变更时重新应用 (只增不删)
if (newState.settings.env !== oldState.settings.env)
  applyConfigEnvironmentVariables()
```

## 七、双层架构的设计权衡

### 7.1 为什么不全放入 AppState

`bootstrap/state.ts` 的注释明确指出全局状态需谨慎。以下数据不适合放入响应式 Store：

| 原因 | 示例 |
|------|------|
| 超高频写入 | `totalCostUSD` 每次 API 响应都更新 |
| 无 UI 消费者 | OpenTelemetry counter 初始化 |
| 需在 Store 之外访问 | `sessionId` 在 bootstrap 阶段就需要 |
| 不可序列化 | `Meter`, `LoggerProvider` 等 OTel 对象 |
| 会话级标记 | `sessionTrustAccepted` 等非 UI 标记 |
| 依赖图位置 | bootstrap 是叶子节点，不能反向依赖 state/ |

### 7.2 状态一致性保证

```
setState(updater)
    |-- prev = state          // 读取当前状态
    |-- next = updater(prev)  // 计算新状态
    |-- Object.is check       // 引用相等跳过
    |-- state = next          // 原子替换
    |-- onChange({new, old})   // 副作用 (CCR同步、设置持久化等)
    |-- listeners.forEach()    // 通知 React 重渲染
```

整个更新过程是同步的，不存在中间状态可见性问题。`onChange` 在通知 React 之前执行，确保副作用在渲染前完成。

### 7.3 测试重置

`resetStateForTests()`（`state.ts:919-930`）在测试环境中将 STATE 完全重置为初始状态：

```typescript
export function resetStateForTests(): void {
  if (process.env.NODE_ENV !== 'test')
    throw new Error('resetStateForTests can only be called in tests')
  Object.entries(getInitialState()).forEach(([key, value]) => {
    STATE[key as keyof State] = value as never
  })
  outputTokensAtTurnStart = 0
  currentTurnTokenBudget = null
  budgetContinuationCount = 0
  sessionSwitched.clear()
}
```
