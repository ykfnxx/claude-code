# 第十一章：上下文管理机制深度分析

> 本文档深入分析 Claude Code 的上下文（Context）管理系统，包括上下文的生命周期、重组策略、压缩管道和缓存机制。

---

## 1. 上下文架构总览

### 1.1 上下文分层模型

Claude Code 采用**四层上下文架构**，每层有不同的生命周期和重组策略：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Context Layer Architecture                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  Layer 4: Working Context (工作上下文)                            │
│  ├─ 当前对话的完整消息序列                                         │
│  ├─ 工具调用结果和中间状态                                         │
│  └─ 生命周期: 单次 Query Loop 迭代                                 │
│                                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  Layer 3: Episodic Context (情景上下文)                           │
│  ├─ 被压缩的历史对话摘要                                           │
│  ├─ Session Memory 和 Magic Docs                                  │
│  └─ 生命周期: 整个 Session，可持久化到磁盘                         │
│                                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  Layer 2: Semantic Context (语义上下文)                           │
│  ├─ 项目知识图谱 (Graphiti)                                        │
│  ├─ 用户偏好和习惯                                                 │
│  └─ 生命周期: 跨 Session 长期存储                                  │
│                                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  Layer 1: System Context (系统上下文)                             │
│  ├─ 系统提示词 (System Prompt)                                     │
│  ├─ 工具定义和环境信息                                             │
│  └─ 生命周期: 应用级，随版本更新                                   │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 上下文组装流水线

每次模型调用前，上下文通过**七步流水线**组装：

```typescript
// src/query.ts: queryLoop() 中的上下文构建流程

async function* queryLoop(...) {
  while (true) {
    // Step 1: Memory Prefetch
    // 启动相关记忆预取（异步，不阻塞）
    startRelevantMemoryPrefetch(messages)
    
    // Step 2: Skill Discovery
    // 预取可能相关的技能
    startSkillDiscoveryPrefetch(messages)
    
    // Step 3: Tool Result Budget
    // 应用工具结果大小预算
    applyToolResultBudget(messages)
    
    // Step 4-6: 压缩管道（见下文详细分析）
    const compactedMessages = await runCompactPipeline(messages)
    
    // Step 7: System Prompt Assembly
    // 组装完整系统提示词
    const fullSystemPrompt = buildFullSystemPrompt(compactedMessages)
    
    // 调用模型
    const response = await callModel({
      system: fullSystemPrompt,
      messages: compactedMessages,
      ...
    })
  }
}
```

## 2. 上下文压缩管道

Claude Code 实现了**四级递进式压缩管道**，按从轻到重的顺序执行：

### 2.1 压缩管道概览

```
原始消息序列
    │
    ▼
┌─────────────────┐  策略: 剪刀式裁剪
│ 1. Snip Compact │  保留: 近期 N 条消息
│   (HISTORY_SNIP)│  丢弃: 更早的历史
└────────┬────────┘  阈值: 基于 token 计数
         │
         ▼
┌─────────────────┐  策略: 缓存编辑 + 时间驱逐
│ 2. Microcompact │  利用: API cache_deleted_input_tokens
│                 │  驱逐: 长时间未引用的工具结果
└────────┬────────┘  触发: 每轮迭代
         │
         ▼
┌─────────────────┐  策略: 折叠已完成调用链
│ 3. Context      │  保留: 输入和最终输出
│    Collapse     │  折叠: 中间 tool_use/tool_result
│(CONTEXT_COLLAPSE)│ 存储: 独立的 collapse store
└────────┬────────┘  特性: 跨 turn 持续
         │
         ▼
┌─────────────────┐  策略: 完整对话摘要
│ 4. Auto-compact │  执行: 调用压缩 agent
│                 │  输出: 结构化摘要 (9段格式)
└─────────────────┘  包含: Circuit breaker 保护
```

### 2.2 第一级：Snip Compact

**文件**: `src/services/compact/snipCompact.ts`

**机制**: "剪刀式"裁剪，保留近期消息，丢弃早期历史

```typescript
// 伪代码示意
function snipCompact(messages: Message[], maxTokens: number): Message[] {
  let tokenCount = estimateTokens(messages)
  
  // 从最早的消息开始移除，直到 token 数达标
  while (tokenCount > maxTokens && messages.length > PRESERVE_RECENT_COUNT) {
    const removed = messages.shift() // 移除最早的消息
    tokenCount -= estimateTokens(removed)
  }
  
  // 在裁剪边界插入摘要标记
  messages.unshift({
    role: 'system',
    content: '[Earlier conversation history summarized below...]',
    type: 'compact_boundary'
  })
  
  return messages
}
```

**特点**:
- 最轻量的压缩策略
- 完全基于客户端 token 估算
- 不依赖 LLM，零延迟
- 保留的消息进入后续压缩阶段

### 2.3 第二级：Microcompact

**位置**: `src/query.ts:414`

**机制**: 结合缓存编辑和时间驱逐的双策略

```
┌─────────────────────────────────────────────────────┐
│                 Microcompact                        │
├─────────────────────────────────────────────────────┤
│                                                      │
│  Strategy A: Cached Editing                         │
│  ┌───────────────────────────────────────────────┐  │
│  │ API Response Fields:                          │  │
│  │ - cache_creation_input_tokens: 新缓存的 tokens │  │
│  │ - cache_read_input_tokens: 读取缓存的 tokens   │  │
│  │ - cache_deleted_input_tokens: 被删除的 tokens  │  │
│  └───────────────────────────────────────────────┘  │
│                                                      │
│  利用 cache_deleted_input_tokens 实现"零成本"压缩     │
│  这些 tokens 已从上下文窗口中移除，不计入输入          │
│                                                      │
├─────────────────────────────────────────────────────┤
│                                                      │
│  Strategy B: Time-based Eviction                    │
│  ┌───────────────────────────────────────────────┐  │
│  │ 1. 追踪每条工具结果的"最后引用时间"             │  │
│  │ 2. 超过 TIMEOUT 未引用的结果被标记为可驱逐      │  │
│  │ 3. 驱逐时保留摘要，丢弃完整内容                 │  │
│  └───────────────────────────────────────────────┘  │
│                                                      │
└─────────────────────────────────────────────────────┘
```

**关键实现细节**:

```typescript
// 延迟边界消息到 API 响应后
// 原因: 使用真实的 cache_deleted_input_tokens 而非估算

const microcompactResult = await microcompact(messages)

// 不立即 yield 边界消息
// 等待 API 响应获取准确的删除 token 数
const response = await callModel({ messages: microcompactResult.messages })

// 响应后 yield 准确的边界消息
if (microcompactResult.boundaryMessage) {
  yield {
    type: 'compact_boundary',
    tokensFreed: response.usage.cache_deleted_input_tokens
  }
}
```

### 2.4 第三级：Context Collapse

**文件**: `src/services/contextCollapse/`

**机制**: 折叠已完成的工具调用链，保留输入和最终输出

**核心概念**: 投影视图（Projected View）

```typescript
// Context Collapse 的核心数据结构
interface CollapseStore {
  // 原始消息的完整历史（永不删除）
  originalMessages: Message[]
  
  // 折叠操作的提交日志
  commitLog: CollapseCommit[]
  
  // 投影视图: 根据 commit log 实时计算
  projectView(): Message[]
}

interface CollapseCommit {
  type: 'fold' | 'unfold' | 'replace'
  messageIds: string[]
  replacement?: Message
  timestamp: number
}
```

**折叠示例**:

```
原始消息序列:
[User] "Find and fix the bug"
[Assistant] tool_use: GrepTool "search pattern"
[Tool] tool_result: Grep results...
[Assistant] tool_use: ReadTool "read file"
[Tool] tool_result: File content...
[Assistant] tool_use: EditTool "fix bug"
[Tool] tool_result: Edit success
[Assistant] "Bug fixed!"

折叠后视图:
[User] "Find and fix the bug"
[Assistant] "Bug fixed!"  // 保留了最终结果
                      // 中间工具调用被折叠到 collapse store
```

**错误恢复用途**:

当 API 返回 413 (Prompt Too Long) 时，Context Collapse 提供轻量恢复路径：

```typescript
function recoverFromOverflow() {
  // 方案 1: 排空已暂存的折叠（轻量）
  const drainedMessages = collapseStore.drainStagedFolds()
  if (drainedMessages.length > 0) {
    messages = drainedMessages
    retry() // 重试
    return
  }
  
  // 方案 2: Reactive Compact（重量）
  return reactiveCompact(messages)
}
```

### 2.5 第四级：Auto-compact

**触发条件**: Token 计数超过阈值

**执行流程**:

```
Token 计数超过阈值
        │
        ▼
┌───────────────────┐
│ Circuit Breaker   │ 检查: 连续失败次数 < MAX
│      Check        │       超过阈值则跳过压缩
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│   Compact Agent   │ 独立 LLM 调用
│   Invocation      │ 模型: claude-sonnet-4-6
└─────────┬─────────┘  预算: 独立的 max turns
          │
          ▼
┌───────────────────┐
│  9-Section Output │ 1. Primary Request
│                   │ 2. Key Technical Concepts
│                   │ 3. Files and Code
│                   │ 4. Errors and Fixes
│                   │ 5. Problem Solving
│                   │ 6. All User Messages
│                   │ 7. Pending Tasks
│                   │ 8. Current Work
│                   │ 9. Optional Next Step
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  Replace History  │ 原始消息 → 摘要消息
│   with Summary    │ 保留: 最近 N 条原始消息
└───────────────────┘  压缩比: 通常 5-10x
```

**Prompt 缓存共享**:

压缩 agent 与主对话共享 prompt 缓存前缀，如果缓存命中可节省大量 token：

```typescript
// 压缩 agent 使用与主对话相同的缓存键
const compactResponse = await anthropic.messages.create({
  model: 'claude-sonnet-4-6',
  system: mainSystemPrompt,  // 相同的系统提示词
  messages: mainMessages,    // 相同的消息前缀
  tools: compactTools,       // 相同的工具集
  // ... 其他相同参数
})
```

## 3. 上下文重组策略

### 3.1 重组触发时机

上下文重组在以下时机触发：

| 时机 | 触发条件 | 重组策略 |
|------|----------|----------|
| **每次迭代开始** | Token 超过阈值 | Snip → Microcompact → Collapse → Auto-compact |
| **API 413 错误** | Prompt Too Long | Collapse drain → Reactive Compact |
| **Max Output Tokens** | 输出被截断 | Escalate 8k→64k → Recovery Loop |
| **Session Resume** | 恢复对话 | 加载持久化上下文 + Rehydrate |
| **Tool Result** | 结果过大 | Tool Result Budget 截断 |

### 3.2 消息优先级矩阵

不同类型的消息在压缩时有不同的保留优先级：

```
Priority Level | Message Type               | Handling
---------------|----------------------------|--------------------------
P0 (Critical)  | 用户最新消息               | 永不压缩
               | 系统指令                   | 永不压缩
               | 待执行的 tool_use          | 永不压缩
---------------|----------------------------|--------------------------
P1 (High)      | 最近 N 条对话历史          | Snip 保留
               | 当前工具调用链             | Collapse 折叠但保留输入输出
---------------|----------------------------|--------------------------
P2 (Medium)    | 工具执行结果               | Microcompact 时间驱逐
               | 中间推理过程               | Auto-compact 摘要
---------------|----------------------------|--------------------------
P3 (Low)       | 已完成的工具调用详情       | Collapse 深度折叠
               | 早期对话历史               | Auto-compact 完整摘要
---------------|----------------------------|--------------------------
```

### 3.3 工具结果预算系统

工具结果有独立的大小预算，防止单个结果占满上下文：

```typescript
// src/query.ts: applyToolResultBudget()

interface ToolResultBudget {
  maxTotalTokens: number      // 工具结果总预算
  maxPerResultTokens: number  // 单个结果预算
  truncationStrategy: 'head' | 'tail' | 'middle'
}

function applyToolResultBudget(messages: Message[], budget: ToolResultBudget) {
  for (const message of messages) {
    if (message.type === 'tool_result') {
      const tokens = estimateTokens(message.content)
      
      if (tokens > budget.maxPerResultTokens) {
        message.content = truncateWithEllipsis(
          message.content,
          budget.maxPerResultTokens,
          budget.truncationStrategy
        )
        message.isTruncated = true
      }
    }
  }
}
```

### 4.2 恢复流程

```typescript
// Session 恢复时的上下文重建

async function resumeSession(sessionId: string): Promise<Context> {
  // 1. 加载转录文件
  const transcript = await loadTranscript(sessionId)
  
  // 2. 重建消息序列
  const messages = transcript.map(entry => reconstructMessage(entry))
  
  // 3. 恢复折叠状态（如果有磁盘缓存）
  const collapseStore = await loadCollapseStore(sessionId)
  if (collapseStore) {
    messages = collapseStore.projectView()
  }
  
  // 4. 注入 Session Memory
  const sessionMemory = await loadSessionMemory()
  const systemPrompt = injectMemory(systemPrompt, sessionMemory)
  
  // 5. 执行一次轻量压缩（可选）
  const compactedMessages = await snipCompact(messages)
  
  return { messages: compactedMessages, systemPrompt }
}
```

## 5. 关键设计洞察

### 5.1 延迟-验证模式

多个压缩策略采用"延迟边界消息"的设计：

```typescript
// 反模式: 立即 yield 估算值
yield { type: 'compact_boundary', tokensFreed: estimatedTokens }

// 正模式: 延迟到 API 响应后 yield 实际值
const response = await callModel(messages)
yield { 
  type: 'compact_boundary', 
  tokensFreed: response.usage.cache_deleted_input_tokens // 实际值
}
```

这个模式在 Microcompact 和 Context Collapse 中都出现，体现了"宁可多等一拍也要确保准确"的设计哲学。

### 5.2 不可变状态替换

每次迭代创建新的 State 对象，而非修改已有字段：

```typescript
// 反模式: 修改现有 state
state.messages = newMessages
state.turnCount++

// 正模式: 创建新 state
state = {
  messages: newMessages,
  turnCount: state.turnCount + 1,
  transition: { reason: 'next_turn' }
}
```

好处：
- 追踪转换原因（`transition` 字段）
- 避免跨迭代的意外状态泄漏
- 便于调试和回放

### 5.3 分级恢复策略

错误恢复采用分层策略，从轻量到重量：

```
Prompt Too Long
    │
    ├── Level 1: Context Collapse drain (轻量, 毫秒级)
    │
    ├── Level 2: Reactive Compact (重量, 秒级)
    │
    └── Level 3: Error yield (最终, 用户可见)
```

这种分层最大程度减少了因临时性 token 超限导致的用户可见错误。

### 5.4 Fire-and-forget 与 Await 的权衡

```typescript
// Transcript 写入: fire-and-forget
// 原因: 不阻塞下一个 content block 的消费
recordTranscript(message) // 不 await

// Token 计数更新: 必须 await
// 原因: 需要准确值做预算检查
const usage = await trackTokenCount(response)
```

## 8. 总结

Claude Code 的上下文管理系统是一个**分层、递进、可恢复**的工程典范：

1. **四级压缩管道**从轻量到重量递进，避免过度压缩
2. **延迟-验证模式**确保数据准确性
3. **不可变状态**保证可追踪性和可测试性
4. **分级恢复**最大程度减少用户可见错误

这个系统的设计体现了对 LLM 应用核心问题的深刻理解：上下文窗口是有限的宝贵资源，需要在保留关键信息和控制成本之间找到最佳平衡。
